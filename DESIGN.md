# LightweightMarkers: design
Status 2026-10-14: 1.0.2 released on GitHub and Nexus (page 1450); 1.0.0 was the first release as Lightweight Markers (0.99.0 and the first 1.0.0 were LightweightStrategicalMarkers), ModID `LightweightMarkers`. 1.0.1 adds "Power cells and containers"; power cells confirmed in game, containers not (no mission found). 1.0.2 adds coloured charge counts, a charge count on deployed ammo crates, light orange plasteel, the preset cartridge icon for large ammo and Markers Improved AIO's idol look (offline only at release), and stimm colours in the HUD (confirmed in game by the user 2026-10-14). Verified: static and offline (`tests/`); independent source review 2026-10-13; all features confirmed in game by the user 2026-10-13. Tagging through our markers and item colours (new in 1.0.0) confirmed in game by the user 2026-10-13.

Lightweight markers for ammo, grenade refills, medical crates, stimms, health stations and chests, built as a lean alternative to Markers Improved AIO (`referensmoddar/markers_aio`).

## Files
- `LightweightMarkers.lua`: settings snapshot, discovery hook and seed, registry, 4 Hz sweep, HUD registration, lifecycle.
- `marker_template.lua`: the world-marker template (factory taking the shared config and state): visuals in `on_enter`, alpha and distance text in `update_function`, widget release in `on_exit`.
- `categories.lua`: pure data: pickup type and interaction type to kind, kind visuals, group settings.
- `LightweightMarkers_data.lua`, `_localization.lua`: options and English text.
- `tests/`: offline harnesses (`tests/README.md`).

## Discovery
- `hook_safe` on `InteracteeExtension.set_interaction_context` (`scripts/extension_systems/interaction/interactee_extension.lua:99`). Spawned units reach it from `init` (`:47`): on a client the pickup husk already carries unit data `pickup_type` (`scripts/extension_systems/unit_templates/pickup_unit_template.lua:172`; extensions are created after `husk_init` returns, `scripts/foundation/managers/extension/extension_manager.lua:170-175`). Level chests and health stations reach it from the `Interactable` component (`scripts/components/interactable.lua:76`), which runs on clients too.
- Classification is one table lookup (`categories.lua`): a pickup by its pickup type only, anything else by interaction type. `deployable_marker` is used only by the deployed medical crate (`medical_crate_deployable_unit_template.lua:6-13`).
- On enable and hot reload the registry is seeded once from `interactee_system:unit_to_extension_map()`, reading every interaction type the unit was given (`_interactions`), since a chest that starts inactive has no active type.
- Registry: dense arrays with swap-remove plus unit to index. Only groups that are on are tracked; a settings change reseeds, so turned-off groups cost nothing.
- Heretical idols are destructibles, not interactables. `CollectiblesManager.on_gameplay_post_init` runs on every peer, picks one idol per section from the level seed and calls `DestructibleExtension:set_collectible_data` with a clone that has `id = 1` (`scripts/managers/collectibles/collectibles_manager.lua:28-66`; called from `gameplay_init_step_pacing.lua:20` without a server check). A `hook_safe` there tracks the idol; the seed takes destructibles whose `_collectible_data` has an `id`. Unpicked candidates keep component data without `id` and stay hidden. An idol is finished when its `_destruction_info.current_stage_index` is 0, which clients get through `rpc_destructible_last_destruction` (`destructible_extension.lua:338-395`).

## Markers near the player
- `mod.update` exists only while enabled; every 0.25 s, if anything is tracked, the sweep runs. It needs `ALIVE` (nil between game states, `scripts/managers/position_lookup/position_lookup_manager.lua:40,44`).
- When the world-markers element is not updating (menus, tactical overlay, cutscenes, dead: `scripts/managers/ui/ui_hud.lua:387`, visibility groups in `scripts/ui/hud/hud_elements_player.lua`), the sweep only purges dead units: a marker flagged `remove` is applied only by `_calculate_markers`, so adding or rebuilding then would pile up widgets.
- Otherwise: squared distance from the HUD camera to each unit (`Unit.world_position`, never `POSITION_LOOKUP` from `mod.update`). Add at marker distance + 5 m, remove beyond + 10 m. An opened chest (`ChestExtension:is_open`, client state through `rpc_chest_set_state`, `chest_system.lua:38-52`) loses its marker and leaves the registry. Health station charges come from `HealthStationExtension:charge_amount` (`health_station_extension.lua:175`, synced by `health_station_system.lua:195,224`); a deployed ammo crate's from its game object field `charges` (set to `num_charges` 4 at spawn, `pickup_unit_template.lua:149-152`; lowered by the server on each use, `pickup_interaction.lua:95-105`), read with `GameSession.game_object_field` through `UnitSpawnerManager:game_object_id` (`unit_spawner_manager.lua:604-606`; husks registered at `:697-700,836`, the id dropped when the game object is destroyed, `:703-708,861-864`). The text and its colour change only when the count does.
- Markers are added with `add_world_marker_unit` (synchronous `on_enter`, `scripts/ui/hud/elements/world_markers/hud_element_world_markers.lua:106-135`) and removed by flagging `remove` (`:277,321-326,479-489`), after which the HUD calls `on_exit`.
- The icon is the interactee's own `interaction_icon()` (`interactee_extension.lua:411-422`), so level overrides match vanilla; the kind's icon is the fallback.
- Setting changes flag every marker for removal; the next sweep rebuilds them with the new settings.

Removed on the user's decision as too much code for a lightweight mod (an 825-line solver, a setting, 17 strings, a template pass and its own harness). Everything needed to bring it back is kept here and in Git.

Restore:
1. The last commit with the feature is `2a4aa20`; `2d94859` removed it. `git revert 2d94859` restores it in one step while later edits allow; otherwise `git checkout 2a4aa20 -- scripts/mods/LightweightMarkers/chest_prediction.lua tests/test_chest_prediction.lua tests/fixtures` and reapply the touch points shown by `git show <removal commit>`.
2. Touch points: `LightweightMarkers.lua` (module load with `math.next_random`, `table.shuffle`, `PickupSettings.pickup_selector` and `pickup_pool_value`; the `prediction` state and `reset_prediction` on disable, unload, mission exit and option off; `prediction_tick` in the sweep; `step_prediction` in `mod.update`; `add_marker` passing `contents`; `apply_prediction` labelling from `chest_item_*`), `marker_template.lua` (the `contents` text pass above the ring; the keep-drawn branch under vanilla's marker, which the crate count still uses), `_data.lua` (checkbox `predict_chest_contents` after Chests), `_localization.lua` (option, tooltip, 13 `chest_item_*` labels), `tests/test_runtime.lua` section 13b, the README's "Chest contents" section and setting row, and `types/SOURCES.md` (consumer of `table.shuffle`).
3. Run both harnesses, then in game: turn on "Predict chest contents" and start a regular mission. Expected: about 2-3 s after spawning in, some chest markers show text such as "Grenades" above them and the console log has one "chest prediction:" line; an opened chest holds at least the named item; close up the text stays above the game's marker. Research (condensed from the local, untracked `analysis/chest-prediction/` report, which also holds the probes, mission dumps and the differential test):
- Two kinds of chest slot. Reserved slots are fixed at mission start by the server-only `_populate_pickups` (`pickup_system.lua:179-193,270-340`): a chest slot that wins an item stores its name in `ChestExtension._containing_pickups` and spawns nothing (`pickup_spawner_extension.lua:264-285`, `chest_extension.lua:68-70`); all plasteel and diamantine in chests is reserved (the open-time roll has no forge branch, `pickup_system.lua:507-584`). Free slots are rolled on opening by `get_rubberband_pickup` (`:371-585`) from the continuing seed stream and live team state, so they are only predictable as "if opened now". Chest RPCs carry only state (`chest_system.lua:8-12,38-52`); the client's `_containing_pickups` stays empty.
- Why a client can compute the reserved part: the level seed is the session seed every peer receives (`state_gameplay.lua:29`, `local_data_sync_state.lua:60-65`; idols and crossroads already depend on it on every peer, `collectibles_manager.lua:29-66`); the RNG is the engine's `math.next_random` (identified as the Numerical Recipes LCG, `types/SOURCES.md`) and seeded `table.shuffle`; pools, spawner components and `percentage_through_level` exist on the client; and every non-chest item of the same pass is a visible network pickup, an exact check of the replay.
- Hazards: string-key `pairs()` order differs per process in the game's LuaJIT 2.1.1771479498 (searched over); exact percentage ties have an unknowable order (shown only when interchangeable); the last section's bound lands within rounding of the highest percentage (both outcomes searched); open paths (Horde, Expeditions) shuffle spawners by address and are not replayable; late joiners miss the mission-start floor.
- Results: km_station (client, seed 374320701): all 54 floor pickups explained, the one opened chest matched. hm_cartel (client, seed 611946183): all 65 floor pickups explained; of 9 chests opened in game, all 6 reserved predictions were exact (grenade, large ammo x2, small ammo, grenade, small diamantine, the last impossible from the open-time roll) and the 3 chests without a reservation were consistent.

Implementation as removed:
- Trigger: in the sweep, while the world-markers element updates, once per `PickupSystem` instance: 2 s of visible HUD after spawning in (the floor pickups have arrived), then `capture` and a coroutine running `solve`. `mod.update` resumes it until 2 ms of the performance counter are spent each frame (`Application.query_performance_counter`/`time_since_query`, as the game's own `gameplay_init_time_slice.lua:9-35`). Offline the whole search is 400-900 category simulations, 0.02-0.06 s without JIT.
- Capture (linear path only, `MainPathManager:path_type`): the level seed (`ComponentSystem:get_level_seed`, `component_system.lua:161`; equal to the session seed on clients), the pool from the client's own `PickupSystem:_fetch_settings` (`pickup_system.lua:74-128`; private, only allocates; covers mission, circumstance, game mode and havoc), `_min_chest_spawner_ratios`, every spawner's components, percentage, chest flag and position, and the floor pickups (`PickupAnimationExtension` entities with unit data `pickup_type`).
- Solve: a port of `_populate_pickups` (guaranteed spawns, the chest-favouring trim, `_spawn_linear_pickup_category`, `_check_spawn`) using the game's `math.next_random`, `table.shuffle` and pickup selectors. It searches the distribution-type, category and name orders (string-key `pairs()` order differs per process; LuaJIT 2.1.1771479498) and both outcomes of the last-section rounding edge, keeping only replays where every floor pickup at a pool spawner is explained (0 contradictions). The edge spawner is the last entry of the usable list, which an earlier category's leftover phase may have shuffled (`pickup_system.lua:709-715,741-749,837`); the second outcome runs only when the edge decided anything. Ties are interchangeable when the tied entries allow the same items, so they are not searched; a tie class whose entries allow different items stops the prediction, and a floor pickup on a spot shared by spawners of different types is not used as evidence. Caps: 20,000 simulations, 64 states, at least 10 explained floor pickups.
- Reviewed 2026-10-14 by an independent agent with a differential test (its own port of `_populate_pickups`, server percentages shifted by up to 4 ULP, random pairs and tie orders; kept in `analysis/chest-prediction/differential.lua`). It found the edge bug above; after the fix: 1000/1000 runs on each fixture with every shown chest right (25,528 labels), 0 wrong chests with 30% of the floor left (half the runs then show nothing), and the tie and co-located guards show nothing or only right chests.
- Result: per chest, the reserved names in slot order, mapped to localized labels (`chest_item_*`); chest markers are rebuilt so `on_enter` takes the label. One `mod:info` line per mission says what was confirmed or why nothing is shown.
- Validated: offline against two real online missions (`tests/test_chest_prediction.lua`), and in game on hm_cartel, where all 6 predicted reserved items were found in the opened chests.

## Template
- Passes: background, ring and icon with vanilla's textures, colours and hand-over sizes (`marker_template.lua`, FRAMES), a distance label and a charge count. One widget definition is cached and shared (`UIWidget.init` clones content, style and passes, `scripts/managers/ui/ui_widget.lua:14-33`).
- `on_enter` writes per-marker settings into the marker's own deep-copied template (`table.clone`, `scripts/foundation/utilities/table.lua:38-52`): position offset (0.8 m for pickups like vanilla's "pickup" visuals, 0 for chests and stations), max distance, line-of-sight check and edge fade (`easing_function` is required, `_get_fade` calls it unguarded).
- `update_function` runs every frame for each live marker after `draw` is decided (`hud_element_world_markers.lua:461-474`, call at `:470`). It allocates nothing and reads no settings. Alpha = line of sight x empty-station dim x (1 - vanilla's alpha); at about zero it sets `draw = false` so the widget is not drawn. Distance text comes from a prebuilt table and changes only when the whole metre does.
- Vanilla recolour: a `hook_safe` on `HudElementWorldMarkers.event_add_world_marker_unit` (once per added marker) finds a new `interaction` marker under the newest id (`_register_marker`, `hud_element_world_markers.lua:168-188`) and swaps the update function in its own template copy (`_template_by_type` clones per marker) for a plain wrapper. The wrapper calls vanilla's update (`world_marker_template_interaction.lua:673-799`), keeps its return value and writes the kind's colour into the icon when the unit is tracked and the kind has its own colour (`recolor`), and the kind's own icon (`own_icon`, large ammo) once its package has loaded: vanilla resets `content.icon` to the interactee's icon at the start of every update (`:680-684`). Vanilla sets that colour only in `setup_marker_by_interaction_type` (`:480-518`, on a visual-type change such as tagging), and a template it re-clones there keeps the wrapper. A per-frame DMF hook was rejected: it allocates a return table and runs xpcall for every interaction marker every frame. Enable wraps existing interaction markers; disable and unload restore the original function. Items of a group that is off are not tracked and keep vanilla's colour.
- Vanilla yield: vanilla's marker for the unit is found through `HudElementInteraction._interaction_units[unit].marker_id` (`scripts/ui/hud/elements/interaction/hud_element_interaction.lua:64-106`) and `_markers_by_id`; its alpha is its line-of-sight alpha times its distance fade unless tagged. While it is fully shown, ours is hidden and its line-of-sight check is off, so it takes no raycasts. A deployed ammo crate with a count (`keep_count`) stays drawn instead: only the background, ring and icon fade by vanilla's alpha (per-pass colour alpha), and the count moves beside vanilla's ring (its `style.ring.size`). A crate's count disappears only with its game object, when the crate is removed.
- Tagging: the template sets `using_smart_tag_system`, `size` (the ring box, set per marker in `on_enter`) and `get_smart_tag_id` (`SmartTagSystem:unit_tag_id`). The tagging HUD then picks the nearest such marker under the crosshair (`hud_element_smart_tagging.lua:599-682`): in line of sight means `not marker.raycast_result`, so with "See markers through walls" (no line-of-sight check) a marker behind a wall is taggable and with it off only a visible one; within the marker's `max_distance`; and only for units with a smart tag extension that `can_tag` (chests and idols have none). The server checks aim and line of sight only for breeds (`smart_tag_system.lua:63-107,739-780`), so pickup tags at any distance are accepted. No per-frame cost: the HUD reads these only while scanning for a tag target.
- Raycasts: the HUD runs 10 every 5th frame for all markers, longest-waiting first (`hud_element_world_markers_settings.lua`, `hud_element_world_markers.lua:11-23,441-447`). Our markers' wait ages at half speed so vanilla markers keep priority.
- `on_exit` releases the widget name in the element that created it (vanilla keeps every marker widget name for the element's lifetime).

## HUD stimm colours
- Own slot: `hook_safe` on `HudElementPlayerWeapon.init` (once per slot element; the handler recreates the element when the slot's item changes, `hud_element_player_weapon_handler.lua:83-121`). It writes the stimm colour (by `_weapon_name`, the inventory item) into the icon style's `default_color`; `set_wield_anim_progress` blends the icon's RGB from `default_color` to the line highlight every frame (`hud_element_player_weapon.lua:408-414,501-518`; called every frame from the handler, `hud_element_player_weapon_handler.lua:280-305`), so the stimm colour shows unwielded and blends to the game's highlight while wielded.
- Teammates: `hook_safe` on `HudElementTeamPlayerPanel._update_pocketable_presentation`, the concrete class (the base method is copied at class creation). The base update calls it only when a pocketable changes (`hud_element_player_panel_base.lua:573-584,1078-1104`), right after caching the player's extensions (`_player_extensions`, `:137-155,165`); the hook reads `slot_pocketable_small` from the inventory component and tints the `pocketable_small` texture colour (`hud_element_team_player_panel_definitions.lua:273-295`). The personal panel has no pocketables (`feature_list.pocketable = false`).
- Only RGB is written (the game animates alpha). A weak-keyed table keeps each tinted colour table's original RGB; enable tints the current HUD's slot and panels (`_player_weapons`, `_player_panels_array`), disable and unload restore them.

## Lifecycle
- New HUD: `hook_safe` on `HudElementWorldMarkers.init` registers the template and forgets ids of the old HUD; `destroy` forgets them. Only one world-markers element exists at a time; the spectator HUD has none.
- Disable: detach `mod.update`, flag all markers, restore vanilla's update, release the icon package, remove the template, clear the registry. Enable: snapshot settings, seed, register into the current HUD; the first sweep requests the icon package and a later one sees it loaded. Releasing after the markers are flagged and vanilla's update is restored is safe: our markers are no longer drawn and vanilla's update puts its own icon back before the next draw.
- Hot reload: the old instance's `on_unload(false)` does the same as disable; the new one's `on_enabled` seeds and registers.
- Leaving `StateGameplay`: flag markers and clear the registry.
- The template name is `<ModID>_marker`, so a renamed copy never removes this one's template.
